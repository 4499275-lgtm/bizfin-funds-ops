## 1. 安装与启动

### 1.1 环境要求
- Node.js ≥ 22.5（推荐 24.x，内置 SQLite，无需安装数据库）
- macOS / Linux / Windows（WSL 亦可）；生产建议 Docker

### 1.2 首次安装
```bash
cd bizfin-funds-ops
npm install          # 还原依赖
npm run build        # 编译 + 拷贝 schema
```

### 1.3 初始化与启动
```bash
# 方式一：CLI 初始化 + 启动（含 Web 控制台）
node dist/src/cli.js init --db data/funds.db
node dist/src/cli.js serve --db data/funds.db --port 8787
# 打开 http://localhost:8787

# 方式二：环境变量启动
DB_FILE=data/funds.db PORT=8787 node dist/src/index.js

# 方式三：Docker
docker compose up --build --detach     # 数据持久化在 ./data
```

### 1.4 首次配置（生产必做）
```bash
# 1) 创建 API Token（仅显示一次，立即保存）
node dist/src/cli.js token-add --db data/funds.db --name ops --role write
# 输出示例：bfo_3fa9…（read=只读 / write=读写 / admin=含规则管理）

# 2) 配置 Webhook 接收方（ERP/数据平台）
node dist/src/cli.js webhook-add --db data/funds.db \
  --url https://erp.example.com/hooks/funds --secret <随机串> --events trusted_status.changed
```
> 配置任意 Token 后系统即离开 open 模式，所有 `/api/v1` 请求需带 `Authorization: Bearer <token>`；控制台静态页不需要。
> 若部署在服务器上，请在前面加反向代理（Nginx）做 HTTPS。

## 2. 日常作业流程（日终勾兑 SOP）

> 核心口径：**单账户 × 单日收入流水**。每天对每个账户重复以下循环。

```
第 1 步 同步订单 → 第 2 步 导入银行流水 → 第 3 步 运行四层评估
→ 第 4 步 处理异常/人工认领 → 第 5 步 复评 → 第 6 步 导出/推送 → 第 7 步 关账确认
```

### 第 1 步：同步业务订单
- **API 方式**：`POST /api/v1/orders/sync`（幂等，可重复调用；重复数据自动去重）
- **文件方式**：控制台「订单模板 CSV」下载 → 填好 → `POST /orders/sync` 或 CLI `import-orders`
- 校验失败的行会被**拒绝**（原因见 rows[].reasons），不影响其他行。

**字段口径**（详见[导入导出](IMPORT-EXPORT.md)）：
- `支付成功`：必须填支付公司 + 支付成功时间；这类订单只参与对应支付公司的清算款认领
- `待确定`：不得填支付公司；这类订单只参与银行转账认领

### 第 2 步：导入银行流水
- 控制台：选择账户与勾兑日 → 选文件 → 可先「仅预览校验」→「校验并导入」
- 支持通用模板与招行 CBS 对账单（自动探测表头），CSV/XLSX 均可
- 行级结果：IMPORTED（进入四层）/ DUPLICATE（重复跳过）/ CONFLICT（同号不同内容，**需人工核查**）/ OUT_OF_SCOPE（支出，仅留原始行）/ REJECTED（校验失败）

> **CONFLICT 处理原则**：银行已入账事实不可覆盖。先核对是否银行冲正/重复导出；确认是新事实时联系实施人员处理，不得直接改库。

### 第 3 步：运行四层评估
- 控制台点「运行四层评估」，或 `POST /evaluations/run`
- 评估完成后每笔流水有：①身份 ②认领 ③异常 ④可信状态（Closed/Processing/Blocked）

### 第 4 步：处理异常与人工认领
打开「异常中心」，按处理路径逐笔消化：

| 异常类型 | 处理动作 |
|---|---|
| 资金来源未识别 | 补充第一层规则（admin 发布 L1 新版本）或人工确认来源后重评估 |
| 支付公司业务归属待确认 | 补同步订单；或确认属于「无应收资金类型」→ 走第二层归属 |
| 支付公司清算金额差异 | 核对手续费预设与成功订单范围；差异来自漏单→补订单；来自费率→发布新手续费版本；**金额未闭合前不要强行关闭**（关闭后会复发） |
| 银行转账多候选/候选待确认 | 「转第二层处理」→ 归属处理对话框选正确订单 → 确认 |
| 银行转账无候选 | 等订单同步；或确认无应收类型（押金/内部往来等，需填凭据） |
| 流水未完成认领 | 第二层补齐剩余金额归属 |
| 手续费规则缺失 | 维护支付公司手续费预设 |
| 已认领订单变化冲突 | 回业务系统核实，审批后重做认领 |

**人工认领（第二层归属）两条路径，二选一**：
- 路径 A：关联业务订单（可拆多笔订单，金额合计 ≤ 流水余额）
- 路径 B：确认无应收资金类型（押金/预收款/内部往来等，需填外部凭据编号）

### 第 5 步：复评
人工动作后系统自动重评估该流水；批量动作后可再手动跑一次「运行四层评估」。已 Closed 的流水不会被自动改写。

### 第 6 步：导出与推送
- 控制台右上导出：勾兑日报表（CSV/XLSX）、可信状态 JSON、异常清单、认领组明细
- 配置了 Webhook 的：可信状态变化会自动推送到 ERP（带 HMAC 签名）

### 第 7 步：关账确认
当日所有流水 `Closed`（或明确挂账的 Blocked 有跟进人）→ 导出日报表归档 → 完成。

## 3. 角色与权限

| 角色 | 能力 |
|---|---|
| `read` | 查询全部数据、导出报表 |
| `write` | 导入、评估、人工认领、异常受理/关闭、Webhook 触发 |
| `admin` | 另加：发布规则/手续费新版本、管理 Webhook 与 Token（Token 需 CLI） |

- 控制台（静态页）不做鉴权，但所有写操作走 `/api/v1`，受 Token 控制；open 模式（未配置任何 Token）仅限本机开发。
- 建议：财务操作员发 `write`，系统管理员持 `admin`，报表消费方发 `read`。

## 4. 备份与运维

```bash
# 备份（SQLite 单文件，WAL 模式）
sqlite3 data/funds.db ".backup 'backup/funds-$(date +%F).db'"

# 巡检
curl -s localhost:8787/health
curl -s -H "Authorization: Bearer $TOKEN" \
  'localhost:8787/api/v1/summary?accountId=ACC-001&reconDate=2026-08-03'

# Webhook 投递失败重试
curl -X POST -H "Authorization: Bearer $TOKEN" localhost:8787/api/v1/webhooks/flush
```
- `data/` 目录即全部业务数据；纳入日常备份。
- 升级版本：替换代码 → `npm install && npm run build` → 重启（schema 兼容自动执行）。

## 5. 常见问题（FAQ）

| 现象 | 原因与处理 |
|---|---|
| API 返回 401 | 未带 Token 或 Token 失效；重新 `token-add` |
| 导入后流水不出现四层结果 | 导入与评估是两个动作；运行「四层评估」 |
| 流水一直 Processing | 正常作业未完成状态；看 ② 认领（NEED_REVIEW→人工认领）或 ③ 异常定位 |
| 支付公司流水 Blocked：业务归属待确认 | 候选日没有该支付公司的成功订单：补同步订单，或确认无应收类型 |
| 差异异常关闭后又出现 | 设计如此：金额未闭合时关闭会复发；先解决差异（补订单/改费率）再评估 |
| 导入 CONFLICT 行 | 同流水号但内容不同：核对银行是否冲正/换日，联系实施处理，不要强行覆盖 |
| Webhook 收不到 | 看 `GET /webhooks/deliveries` 状态与 last_error；`POST /webhooks/flush` 重试 |
| XLSX 打开乱码 | 使用 WPS/Excel 2016+，或改用 CSV（UTF-8） |

## 6. 演示与培训

```bash
# 一键导入演示场景并完成评估（不污染真实数据，见控制台顶部按钮）
node dist/src/cli.js seed-demo --db data/demo.db --scene flower    # 鲜花：10 Closed / 3 Blocked
node dist/src/cli.js seed-demo --db data/demo.db --scene property  # 物业：7 自动闭环 + 4 人工 + 2 异常
```

推荐演示脚本（物业场景最能讲清边界）：
1. 初始 7 笔自动闭环 → 指出通联/财付通的**汇总认领**（不伪造逐笔对应）
2. 支付宝预付卡 → 异常中心「转第二层处理」→ 无应收类型「预收款」+凭据 → Closed（**没有订单也能合规闭环**）
3. 银联商务差异 25 元 → 讲差异定位与外部核查路径（不要当场关闭）
4. 张伟转账 → 讲「未识别 ≠ 银行转账」，第一层规则覆盖不足的处理方式

## 7. 红线与边界（务必培训到位）

- 平台只处理**收入**流水；付出方向、支付公司每日明细、退款、会计凭证、收入确认**均不在范围**
- 平台不回写业务系统支付状态、不创建订单/应收/业务主数据
- 银行事实不可覆盖；人工决策不可被自动重评估静默改写；异常关闭必须有依据
- 可信资金状态 ≠ 财务收入确认；Closed 只代表「资金身份、业务归属已受控、无阻塞」
